# 应用模块设计讨论稿

> 后续用户已明确修正架构：通用框架 + 应用适配描述。不同应用的退出菜单路径允许写入 Adapter 配置，由同一引擎执行；Adapter Builder 负责录制并生成配置。下文“不得按应用描述退出路径”等旧限制已被此决定替代。当前实现进度见 `docs/testing/2026-09-16-switcher-v2-native.md`。

状态：产品方案逐步确认中，尚未形成最终实施计划。本文记录本轮已确认的选择；待确认内容不视为开发授权或已实现能力。

## 已确认的产品方案

### 首页与应用管理

- 核心用途是选择保存的账号，为桌面应用填写登录资料；QQ 首版围绕单个会话切换账号，不设计并行多账号登录。
- 整体设计以多应用通用为原则。账号管理、权限、切换流程、提示、任务控制及输入执行共用；只有登录模块的实际差异需要按应用适配。
- 首页只展示用户主动添加的应用，使用图标卡片，显示名称和账号数量，并提供搜索及“添加应用”。
- 安装应用的扫描结果放在添加窗口中；支持搜索、多选添加，找不到时可手动选择应用文件。添加应用后可以稍后再添加账号。
- 点击应用进入独立的完整账号页面，提供返回入口；路径、版本等放在“应用信息”中。
- 从首页移除应用只取消展示，保留账号和密码；再次添加同一应用恢复原账号。删除账号是另一项操作。

### 已确认的应用缺失处理

- 已添加应用被移动或卸载后，首页保留卡片并标注“未找到应用”，不删除账号或凭据。
- 账号页面仍支持查看账号资料、编辑和复制；填写／登录暂不可用，提供“重新定位”入口。
- 用户重新选择同一应用，或重新安装后经身份核验恢复关联，复用原应用记录与账号。
- 选择其他应用时明确提示不匹配，不将原账号改绑到不同应用。应用身份核验未通过时不执行填写。

### 升级迁移规则

- 全部旧账号、密码及凭据引用保留。
- 已有账号且未隐藏的应用迁入新版首页；原来隐藏的应用仍不显示。
- 仅扫描到且没有账号的应用放入“添加应用”列表，不自动进入首页。历史手动导入状态不足以可靠还原主动添加意图，不据此批量加入首页。
- 首次上线真实自动提交时，旧账号的自动提交统一关闭一次，并简短说明；之后由用户逐个开启。迁移须只执行一次，不能在以后启动或扫描时覆盖用户选择。

### 账号管理细节

- 添加、编辑账号使用弹窗，字段为账号名称、用户名、密码及自动提交选项。
- 新建账号的自动提交默认关闭。
- 账号列表展示名称与用户名，不直接显示密码。
- 每个账号提供明确的主按钮：默认“填写”，开启自动提交后显示“登录”。
- “更多”菜单提供编辑、删除、复制用户名、复制密码。
- 复制密码后 30 秒清理，仅清理本次复制且未被替换的剪贴板内容。

### 填写过程

- 打开或唤醒目标应用，缺少系统权限时提供简短引导。
- 首次遇到某个登录界面，或界面明显变化时，展示识别出的填写位置，由用户确认。
- 相同界面后续通过校验后可以直接填写。只在该账号启用自动提交时点击登录。
- 扫码页由用户手动切换到密码登录，再重新点击“填写”。验证码、设备确认等由用户完成。
- QQ 不调用“多账号登录”或新开并行登录实例。
- 退出当前账号采用通用能力判断：能可靠识别并执行退出时，由 LoginDeck 提示用户并在确认后操作；不能可靠处理时，交给用户在目标应用中退出。不得为了 QQ 或其他应用另写专属退出流程。
- 识别不确定，或填写期间用户切换窗口时停止操作。
- 区分“已填写”“已提交”和“登录成功”；只有确认进入登录后的状态，才报告成功。

### 通用退出与登录适配的边界

产品原则已确认，下列细节为按此原则整理的设计方案。

- macOS 辅助功能没有标准的“退出当前账号”动作。目前尚无本项目跨应用验证结果，因此默认交由用户在目标应用中退出；只有同一套通用规则完成跨应用验证后，才开放符合条件的辅助退出。
- 已处于登录页时直接进入登录流程；已登录时检查是否存在明确的账号退出操作；状态不明时请用户手动准备登录页。
- 通用退出先通过本机辅助功能检查当前应用的菜单、按钮及可执行动作。仅接受语义明确、可用且归属于目标实例的账号退出入口；普通的“退出应用”“关闭窗口”、含义不明的“注销”以及“退出所有设备”不能视为本次账号退出。
- 识别结果不确定、存在多个无法区分的候选、入口不可访问或需要应用特有的设置导航时，回退手动操作。不以每个应用专用的菜单路径、坐标或退出脚本补齐兼容性。
- 操作前统一提示，例如“将退出 QQ 当前账号，并为‘工作账号’填写登录资料”，提供继续和取消。任务仍遵循所选账号的自动提交设置；确认退出不等于开启自动提交。
- 退出前先检查目标账号资料、所需权限及配置。执行一次退出动作后重新检查页面；出现不能可靠处理的二次确认、超时或页面变化时暂停，交给目标应用处理，不反复点击退出。
- 手动退出或完成应用自身确认后，由用户点击“继续”并重新检查登录页，避免后台等待期间自行开始输入。
- 退出后登录失败时如实显示“已退出，未完成新账号登录”，提供重试或手动完成；不能报告切换成功，也不能承诺自动恢复旧会话。
- 退出阶段只依靠本机通用控件检查；本轮 AI 辅助仍用于登录界面识别，不上传已登录的业务界面来寻找退出入口。
- 登录适配可以描述各应用的用户名/密码控件、分步登录流程、提交按钮及验证或成功状态；复用统一的凭据读取、首次确认、窗口校验和输入执行，不复制整套应用流程。

### 已确认的任务交互

- 统一使用简洁的任务进度弹窗，展示打开应用、识别登录页、填写账号等阶段，并提供取消。
- 需要人工操作时明确说明原因，用户完成退出账号、切换密码登录等操作后点击“继续检查”，重新核验目标窗口。
- 识别失败或接口不可用时展示具体原因，提供重试、手动复制和取消。
- 结果区分已填写、已提交和登录成功，未知结果不能报成功。
- 一次只执行一个任务。用户切换到其他窗口时停止输入，返回后由用户主动继续，并重新检查目标窗口和已执行步骤，避免重复输入或提交。
- 取消只停止后续动作，不自动撤销已经发生的填写或退出；明确告知已完成的步骤。
- 任务弹窗只在需要用户确认时获取焦点，执行填写时由目标应用保持前台；不能把流程自身的确认窗口切换当成用户异常切换。

### 识别与服务配置补充

- 用户已要求停止模型测试，后续不再发起测试请求；保留现有结果，QQ 真实截图仍未完成识别验证。
- 正式配置支持自定义服务地址、API 密钥和模型名称，不限定官方服务商，不写死某个模型。用户提供的中转站地址为 `https://api.apikey.fan`；其图片接口协议及可用模型尚未核实，不视为已经接入。

- 先通过 macOS 辅助功能识别输入框、按钮等控件。
- AI 辅助识别为可选功能，默认关闭；本机无法识别时提供主动使用 AI 或手动复制的入口。
- 用户配置模型服务并主动选择后才调用 AI；提前说明截图接收方及可能的费用。
- 账号密码不发送给模型，截图必须检查是否含已有敏感内容；无法可靠处理时停止上传。
- AI 和本机识别都遵循首次确认及界面变化后重新确认的规则。
- 用户已有第三方中转站接口，首版优先接入用户的服务；具体协议、图片输入方式和模型需依据该服务文档核实，不能仅凭“中转站”推定兼容。

### AI 服务配置方案

以下是根据用户已有第三方接口整理的配置方案，具体协议待文档核实。

- 设置主页面保留简洁的 AI 辅助识别入口，服务配置放在独立页面。
- 配置服务地址、模型名称及 API 密钥。密钥保存在本机钥匙串；普通设置只保存密钥引用，不将密钥写入模板或日志。
- “测试连接”提供进行中、成功和明确失败反馈。使用内置无敏感内容的模拟登录图片，验证鉴权、图片输入及可解析的识别结果；只有文字请求成功不算通过。
- 用户尚未配置服务、关闭 AI 或服务不可用时，本机识别与账号管理仍可使用。
- 请求模型识别前展示待上传图片与目标服务，由用户确认。无法可靠排除图片中已有敏感内容时，不发送该图片。
- 不因中转站故障自动切换到其他服务或模型。具体接口路径、鉴权方式和结果解析在核实该站文档后确定。

### 首批适配与验证

- 首批仅适配、验证 QQ；微信暂不纳入本轮。
- 验证账号密码填写、首次位置确认、可选自动提交、验证码交接及窗口变化时停止。
- 首批适配目标不代表当前代码已支持自动填写，也不代表其他应用均可自动填写。

## 2026-09-16 的实际检查

- 本机 QQ 为 7.0.1（52892），Bundle ID 为 `com.tencent.qq`。
- QQ 当前会话窗口通过辅助功能仅暴露外层窗口、分组及系统按钮；这不能直接证明独立登录窗口的控件暴露情况。
- QQ 的独立登录表单尚未完成控件检查，也未执行凭据填写或提交。因此不能把本轮检查记作自动填写兼容性通过。
- 项目已有应用发现、账号管理、凭据存储及验证应用身份后启动的能力；没有窗口识别、输入执行、AI Provider 或登录任务状态机的实际实现。
- 当前启动接口会返回一个进程 PID，但尚无登录窗口绑定与填写前验证能力。
- macOS SDK 的标准辅助功能动作是控件级的按下、显示菜单、取消等，没有账号登出语义。动作超时也不代表动作没有发生，退出后必须重新观察，不能盲目重试。
- 已按用户要求试用硅基流动免费 `Qwen/Qwen3.5-4B`。图片输入和严格 JSON 请求可用，但第二轮六个虚构场景仅两个满足完整判定条件，两个正常登录页均无法提供完整可用的控件位置；暂不将其用于自动填写坐标。详见 `docs/testing/2026-09-16-siliconflow-vision/README.md`。
- Google Gemini 3.6 Flash 使用同一组样本，4 项通过，中文登录与已登录主界面两项因 HTTP 503 未完成验证；英文登录页三个控件均定位通过。可继续作为 AI 候选评估，尚未确认真实 QQ 兼容性。Gemini 2.5 Flash 则被接口明确拒绝向新用户提供。详见 `docs/testing/2026-09-16-gemini-vision/README.md`。

## 实施时需要解决的事项

以下是技术分析及建议，尚不是最终实施方案。

- 为“用户主动添加”增加独立状态；扫描更新元数据时不得把已移除的应用重新加入首页。重新添加应复用原应用身份及账号。
- 历史扫描来源不能准确还原主动添加意图；按已确认的升级规则迁移，仅将有账号且未隐藏的应用加入首页，保留全部账号与凭据引用。
- 旧账号自动提交按已确认规则一次性关闭，并在迁移后保留用户新选择。
- 登录任务必须绑定已核验的进程实例和具体窗口。如果用户自行打开多个 QQ 实例而无法唯一确定目标，应停止并提示，不能按 Bundle ID 随意选一个；本轮不新增并行多账号登录能力。
- 同一时刻仅执行一个填写任务，提供可取消的进度反馈；取消、失去焦点和窗口变化后不得继续输入。
- 密码通过后端凭据存储读取，不经系统剪贴板自动填入，不进入任务日志或模型请求。
- 需要覆盖应用添加/移除与数据迁移、账号弹窗、剪贴板清理、首次确认、权限拒绝、失败恢复，以及 QQ 切换账号时的目标绑定测试。
- 通用退出使用同一套实现验证不同应用形态的测试界面；覆盖明确退出入口、只有关闭/退出应用入口、不可访问或含糊入口、取消确认、退出后未到登录页，以及新账号登录失败。仅在 QQ 上成功不能视为通用性验证通过。
- 最终应进行黑盒界面测试；真实账号登录及外部验证须与用户另行约定，不能把虚构记录的本地管理测试当作 QQ 登录成功验证。
